TronBrowser 3.13: a Pit button, built like the Tor one, and an engine of its own

Moshpit names such as chovy.hacker or anything.moshpit live outside the ICANN root, so a normal resolver has no answer for them. Until now the way to reach them in TronBrowser was moshcode dns enable, which teaches the whole machine but needs root and rewrites the resolver config. On a laptop where DNS is not yours to change, that was the end of the road.

TronBrowser 3.13 adds a 🤘 Pit button in the AI sidebar, right next to 🧅 Tor. Click it and Moshpit names resolve in the running session, http and https. Click it again and they stop. Nothing on the machine changes.

How it works

It is the Tor toggle's design, reused. The launcher already runs a small loopback helper at every browser start. That helper now serves three more routes. Start binds a SOCKS5 resolver on 127.0.0.1:9081 that answers names through the public Moshpit DNS-over-HTTPS endpoint and relays the connection. Nothing listens and nothing is contacted until the button asks.

The extension then installs a PAC script with one rule in it. If the system resolver can answer the host, the connection goes direct, untouched. Only a host the system has no answer for is sent to the pit resolver. That is the house policy for Moshpit: clearnet wins, the pit is the fallback. A resolver that silently redirected a domain which already works would be indistinguishable from a hijack.

The rule also sidesteps a problem an ending list cannot solve. The registry holds about 17,600 endings, and real TLDs like .io and .dev are among them. A list saying "this ending belongs to the pit" cannot tell you whether github.io is a Moshpit name. Asking the system resolver first can.

What about https

No public certificate authority issues for a name outside the ICANN root, so a Moshpit origin serves a self-signed certificate for its own name, and the registry keeps a fingerprint of that site's key. The first time you open https on a pit name, the helper reads the certificate the site serves, checks its key against the registry's fingerprint, refuses anything marked as a certificate authority, and adds the certificate to the browser's trust store for that one name. It happens before the browser's TLS handshake, so the page loads clean the first time. You do nothing.

Why TronBrowser now ships its own engine

That last part fell over on the Flathub build of ungoogled-chromium. It ignores the user's certificate trust store entirely: the certificate sat in the exact database the browser opened, and it still refused it. The same release as a portable build accepts it. So the installer now fetches that portable build, the one the Docker image already runs, and the launcher prefers it over whatever Chromium a machine happens to have. On Ubuntu that also needs a small AppArmor profile so the engine can sandbox itself, which the installer writes once. The launcher tests the engine with a throwaway headless start before using it and falls back if it cannot run, so a missing library is a fallback, never a crash.

Two things worth knowing. Tor and the pit are exclusive: the PAC asks the system resolver about every host, and under Tor that would leak every lookup, so turning Tor on takes the pit down. And the first click after an upgrade can land while the launcher is still swapping in the new helper; the button waits that out instead of failing.

Upgrade with tron upgrade, or grab the build from the release page. The design notes, including everything that did not work along the way, are in docs/moshpit-pit-toggle.md. Test it by opening https://chovy.hacker.
