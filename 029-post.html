ThreatCrush has a GitHub App listing now. I am going to be straight about what is behind it, because the honest version is more useful than the launch version: the listing is real, the permission set is deliberate, and the backend does not exist yet.

Here is the whole app, from the public API:

$ gh api /apps/threatcrush --jq '{description, permissions, events}'
{
  "description": "ThreatCrush.com free security scan (upgrade for AI analysis)",
  "permissions": {
    "metadata": "read",
    "pull_requests": "read"
  },
  "events": []
}

Two read permissions and no webhook subscriptions. That is the entire grant.

Deciding the permissions first

metadata: read is mandatory. Every GitHub App gets it and you cannot decline it. It covers the repository name, default branch, visibility and topics, and nothing inside the repo.

pull_requests: read is the one I chose. It reaches the list of files in a pull request and the patch for each one. It does not reach your default branch, your history, your other branches, or any file that is not in the diff.

There is no contents permission on that list, which is the point. A scanner with contents: read on a private repo is holding your entire codebase, on every machine that ever sees the installation token. Most security apps ask for it, most people click through, and now the vendor has a copy of your source and you have a supply chain exposure you did not have last week.

Almost none of that is needed to review a diff. If the job is to say whether the change you are about to merge adds a hardcoded credential, the change is the only input. I picked the permissions before writing the integration so that the narrow path is the only one available to me later. It is much harder to widen a published listing than to start wide and promise restraint.

What it does today, which is nothing

No client credentials, so the install code cannot be exchanged. No stored installation id, no installation webhook, no scanning. Install it and you get a confirmation page that tells you to use the CLI, which runs locally and sends your code nowhere:

npm install -g --ignore-scripts @profullstack/threatcrush
threatcrush scan . --format json

That gap is the work, and it is work from zero.

The setup URL 404

When someone installs an app, GitHub bounces them to your setup URL with ?code=...&installation_id=...&setup_action=install. Mine points at https://threatcrush.com/api. In a Next app, app/api/ full of child routes gives you no route at /api itself, so every single installer landed on a 404 and nothing in the codebase hinted at it. Fixed today:

$ curl -so /dev/null -w '%{http_code} %{redirect_url}\n' \
    'https://threatcrush.com/api?code=x&installation_id=1&setup_action=install'
302 https://threatcrush.com/github/installed?setup_action=install&installation_id=1

The code is dropped on purpose rather than carried into the page URL, where it would leak through the Referer header and browser history.

Telling a draft listing from a broken link

A published Marketplace listing answers 200 to a logged out request. A draft one answers 404, including to you when you are not signed in as the owner, which looks exactly like a typo. Compare against a listing you know is live:

$ curl -so /dev/null -w '%{http_code}\n' https://github.com/marketplace/snyk
200
$ curl -so /dev/null -w '%{http_code}\n' https://github.com/marketplace/threatcrush
404

So mine is still in review. The app installs either way, at github.com/apps/threatcrush, and until the backend lands it will politely do nothing.
