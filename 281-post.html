Reverse engineering with AI: the browser already handed you the source

2026-11-25, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes and a test run today, then edited by me.

back to my blog postings

Builder.io just posted How to reverse engineer a website with AI. They point a coding agent at the wave on Stripe’s homepage, it reads the minified WebGL shaders, splits the effect into layers with knobs, and then rebuilds it in your own project with fresh code. It’s a good walkthrough. Their tool is called /remix.

It made me realise how much of what we do every day is reverse engineering, and that we never call it that.

The thing everyone forgets

Everything that runs in a browser has already been sent to you. The HTML, the CSS, the JavaScript, the shaders, the API calls. Minifying it was never protection, it was compression. The only thing stopping you from reading it was time: nobody wants to untangle 6,000 characters of function(t,e){var a=... by hand.

An agent doesn’t mind. It reads minified code like you read a menu.

The one thing it can’t see is the server. But the browser shows you every request the client makes, so you can usually work out what the server does from the outside too.

Teardown 1: a competitor’s product, in one file

In August we looked at device-test.com, a free site that tests your camera, mic, keyboard, gamepad and so on. An agent pulled the page apart and found that one 129 KB app.js drove every test. From that one file it mapped every test to the browser API behind it, and found four holes:

  • It wasn’t a PWA. A tool for diagnosing a broken machine needed a working network.
  • No Windows or Linux app.
  • Its “network speed test” timed five requests to a CSS file that returns 404, then measured download speed by fetching its own 129 KB script once. On any fast connection that’s a latency reading with a megabits label on it.
  • Closed source, while asking for your camera, microphone, location and Bluetooth.

That teardown became the spec for d3vices: open source, works offline, and a network test that actually tests the network. We didn’t copy a line. We read how theirs worked, wrote down what was wrong with it, and built ours from the notes.

Teardown 2: a company, not a website

Last week I wanted CoinPay to offer what OneDosh, a consumer app, does: a US bank account for people outside the US. OneDosh has no API and no partner program, so there was nothing to integrate.

The agent read their terms of service instead. Their legal pages linked to the banking-infrastructure company underneath them. That company sells exactly this as an API, in ninety countries. The agent filled in their sales form and built the module the same afternoon. I wrote that up here.

Same skill as reading a shader: the evidence was public, it just took patience nobody had before.

Teardown 3: our own tracker, minified

To show what this looks like, I took our own analytics script, crawlproof.com/stats.js, and minified it to 6,715 characters of soup. It’s ours, so nobody has to wonder whose code it is, and you can check every claim below against the readable original.

I asked the agent what it does. Here’s what it read back from the minified version:

  • It’s a pageview and event tracker that posts JSON to crawlproof.com/api/track with credentials: "omit", so no cookies go along.
  • It stores two things in localStorage: a random visitor id (crawlproof.visitor) and a session id with a last-seen timestamp (crawlproof.session, stored as id|time).
  • A session is 30 minutes of inactivity. The constant is U=18e5 milliseconds. Every event pushes the timestamp forward.
  • Each event sends the page URL, referrer, viewport, screen size, language and timezone. No IP fingerprinting in the client, no canvas tricks.
  • It tracks pageviews (including single-page-app navigation, by wrapping history.pushState and replaceState), scroll depth at 25/50/75/100%, form submits, and clicks, which it sorts into downloads, outbound links, internal links and buttons.
  • It can load more code: a careers widget, but only on a /careers page or one marked data-cp-careers, and a WebMCP module, but only if the browser exposes navigator.modelContext for AI agents.
  • One sneaky bit: a crp_actor URL parameter gets saved as an “actor” id and then wiped from the address bar with history.replaceState. That’s how a logged-in user from an email link gets tied to their visits.

All correct. That last point is exactly what you want an auditor to notice, and I’m glad it did. If you’re ever wondering what a third-party script on your site is really doing, this is a two-minute job now.

And on c0mpute?

The obvious next step is to stop sending code to a frontier model and run the read on open models on c0mpute, our peer-to-peer network. There are good reasons to want that. A security team auditing a vendor’s script, or a lawyer’s client’s app, may not want to paste it into someone else’s cloud. And c0mpute has coder models running right now: qwen3-coder 30B, qwen2.5-coder 14B and 7B, devstral 24B, deepseek-coder-v2.

So I tried it today, with the same minified file. Honest result:

  • A one-line test prompt came back fine.
  • The full 6.7 KB file timed out on the 30B and the 14B coder models, through both the API and the CLI.
  • One run with chat plugins switched on went off to search Microsoft’s docs for “JavaScript minification” and never came back to the question.
  • Even a 1.5 KB slice timed out on the 7B model.

So today, the reading is done by a frontier agent, and c0mpute isn’t ready for long code prompts yet. That’s ours to fix. The network routes small chats well and long-context code badly. When it handles a whole bundle, I’ll post the same test again with the numbers.

Rules I’d keep

  • Learn from it, rebuild from your notes. Builder says the same: don’t paste someone’s minified code or shaders into your project. Write down how it works and build your own. It’s cleaner, and it’s yours.
  • Logos, fonts, images and copy belong to them. Behaviour you can learn from. Assets you can’t take.
  • Read the terms. Reading what a site sends you is fine. Hammering private APIs, getting around logins or breaking rate limits is a different thing.
  • Point it at yourself first. The most useful teardown I did this year was of our own script. You find out what you’re actually shipping.
