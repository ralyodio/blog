The HTML we have been writing around

How this was written: drafted with an AI assistant from my own notes, then edited by me.

Chris Coyier posted a roundup of what HTML has picked up by the middle of this year: New Things You Should Know About HTML Here in Mid 2026. It is the good kind of roundup. Every entry has syntax and an honest note about which engines actually ship it, instead of a list of names you then have to go research.

Reading it, the thing that kept happening was recognition. A lot of these features are code we already wrote by hand. Not code that resembles ours. The same job.

Permissions, which is the entry I care most about

We run d3vices.com, a bench of browser capability tests. The tests directory has 25 files in it, and geolocation.js, camera.js and microphone.js are three of them. Each is a button, a permission request, and then a lot of handling for whatever the browser decides to do next.

The API call was never the hard part. navigator.geolocation.watchPosition is one line. The hard part is the state after a denial, where the API simply stops answering and the only route back is a lock icon in browser chrome that the page has no way to point at. Every product I have shipped that asks for a camera has a support burden made entirely of that one moment.

The post covers <geolocation> and <usermedia>, elements that wrap the triggering button and own that flow, with a cited 65% recovery rate against 10% for the old prompt. If that number survives contact with the real world it is the most valuable item on the whole list. Chrome only so far, and it falls back to behaving like a <span>, so wrapping a button we already have costs nothing to try.

150 lines that want to be one tag

PairUX has a hook called usePWAInstall. It is 152 lines. It listens for beforeinstallprompt, stashes the event because you only get it once, works out whether the app is already installed, remembers a dismissal in localStorage for seven days, and exposes a canInstall flag so a button knows whether to render at all. All of it is scaffolding around one browser event that fires when it feels like it.

<install> is that button. Same story with appearance: base-select and ::picker(select), which retire the custom dropdown component that nearly every site we run carries its own version of. Safari shipping that one is what moves it from interesting to plannable.

The widget problem, twice

Two entries hit the same nerve.

CrawlProof serves ad units through a script tag on other people's pages. The unit renders into an iframe with a sandbox attribute that permits popups and nothing else, because on a stranger's page there is no other way to be sure our styles and theirs stay out of each other. Scoped custom element registries are that isolation without paying for an iframe.

The other one is <persistentwidget>. Our media-streamer app has contexts/podcast-player.tsx, 500 lines of React context whose entire reason to exist is keeping a single <audio> element alive across route changes so your episode does not stop when you click a link. That is a widget that survives navigation, which is exactly what the proposed tag does. It is only at intent-to-prototype, so this is a wish and not a plan, but it is the cleanest example on the list of a framework pattern that exists solely because HTML was missing a behavior.

Free wins we are not taking

hidden="until-found" is authored in zero files across our repos. I checked. Collapsed FAQ and detail sections all over our sites are invisible to browser find-in-page for no reason.

sizes="auto" retires the hand-maintained media query string in a sizes attribute, which is a thing nobody has ever updated after writing it once. Lazy-loaded images only, so hero images still need real numbers.

focusgroup gives you the roving tabindex pattern declaratively. We have 116 Svelte and React files that touch tabindex. Most roving tabindex code in the world is an arrow key switch statement somebody wrote once and never tested with a screen reader.

And <h1> inside <section> no longer gets shrunk by the user agent stylesheet, which already happened to all of us whether we noticed or not.

Why this is the direction I want

Almost every item here is HTML absorbing work that a framework, a component library, or 150 lines of ours had been doing. We keep house packages for anything we build twice, and the best possible fate for a house package is getting deleted because the platform grew the feature.

The honest caveat is that most of this is Chrome first, <model> is Safari only, and reference target sits behind flags in two engines. So none of it is a rewrite. It is a list to check before writing the next component, which is why the original post is worth twenty minutes of your time rather than a skim.
