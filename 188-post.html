MediaAnalyzer describes and sorts photo, video and document libraries, and it bills prepaid credit per file. Until today the billing page had a balance and no way to add to it, so topping up meant sending an email. That is fixed. Pick an amount, pick a coin, pay on the hosted checkout.

Credit is sold at face value. $25 buys $25 of describing. Nine coins work: USDC on Solana, Polygon or Ethereum, USDT on Solana, plus BTC, ETH, SOL, POL and DOGE.

Three things came out of building it that are worth writing down.

The webhook is nested, and our shared code did not know

CoinPay posts a signed webhook when a payment confirms. The body looks like this:

{ "id": "evt_<paymentId>_<ts>",
  "type": "payment.confirmed",
  "data": { "payment_id": "...", "status": "confirmed", "metadata": { ... } } }

The top level id is the event, not the payment. We have a payments module shared between two other sites that reads payload.id, payload.status and payload.metadata flat, one level up. Against a real webhook that resolves to the event id, finds no status and no metadata, and throws inside a handler nobody watches.

Reading the flat fields first is worse than throwing, because it matches the event id and would credit against a reference that does not exist. Read data first, fall back to flat for the older test sender.

Never trust the amount on the wire

The webhook says money arrived. It does not get to say what you agreed to sell. The amount of credit is written down when the checkout opens and read back from that row at settlement.

To prove it, the production test sent a confirmed webhook claiming 999,000,000 micros of credit against a payment that had sold 25,000,000. The account got $25.

A payment can only be credited once, three ways over

Webhook retries are normal, so the interesting question is not whether a duplicate arrives but how many independent things stop it paying out twice.

  1. Only settled statuses grant anything. Not detected, which fires before the

transaction is safe from a reorg.

  1. The payment row is locked, and credit is granted only on the transition into a

settled status. A retry sees a row that is already confirmed.

  1. A unique index on the ledger refuses a second line for the same payment whatever

the code above does.

Two confirmed webhooks for the same payment, in production, produced one ledger line.

One more thing that would have bitten every buyer

USDC on Base led the coin picker in the first draft. CoinPay resolves the payee from the business wallet for that chain, and there is no Base wallet on the account, so every buyer taking the default would have met a 400 after choosing their amount and their coin. The offered list is now a subset of the wallets that actually exist, and a test holds it there.

Worth remembering for anything that hands a buyer a list of options: the option has to be checked against the thing that fulfils it, not against the vendor's list of what is theoretically supported.
