A dead A record and six modules that never loaded

How this was written: drafted with an AI assistant from my own notes, then edited by me.

Someone asked why mcp.profullstack.com was down. The answer took about four minutes to find and was duller than I wanted: the A record pointed at a server that no longer exists.

$ dig +short mcp.profullstack.com
104.36.23.197

$ ping -c3 104.36.23.197
3 packets transmitted, 0 received, 100% packet loss

That IP is an old VPS in Phoenix. It is still sitting in my SSH config as Host profullstack on port 2048, and it is still hardcoded as the deploy target in three other repos of mine. When everything else moved to Railway, this one subdomain did not come along. Nothing was serving it, so the request just hung until curl gave up.

No monitoring caught it because nothing was watching that hostname. The box did not return errors. It stopped answering entirely, which reads as a network problem rather than an outage, and I had no reason to look.

The pnpm trap that hides itself

Moving it to a new host should have been twenty minutes. It was not, because of one detail in how this repo is laid out. Every module under mcp_modules/ is its own pnpm project with its own lockfile. A root pnpm install does not reach any of them.

Here is the part worth remembering. When a module's dependencies are missing, nothing crashes. The server boots. /health returns 200. The module simply logs a line at warn level and never registers:

Could not load metadata from index.js for module qr-generator:
Cannot find package 'qrcode'

Six modules were dead that way and every health check I had was green. A liveness probe that only asks whether the process is up will tell you the truth and still mislead you. Now the deploy script loops over the module directories and installs each one, then prints the count it actually loaded.

Bun loaded 27, Node loaded 26

I tried both runtimes before wiring up systemd. Node registered 26 modules. Bun registered 27. The gap is one line in the csvjson module:

import { version } from './package.json';

Bun supports JSON imports natively. Node rejects that without an import attribute, so the module throws on load and disappears. The right fix is to correct the import. The fix I shipped today was to run Bun, which I was leaning toward anyway.

Two things about mise and systemd

Both cost me a few minutes, so they are written down now. The mise shims directory is on the login PATH, but the mise binary itself lives in ~/.local/bin, which is not. So node resolves over SSH while npm i -g dies with mise: command not found.

And systemd does not run a login shell, so ExecStart needs the absolute path from mise which bun. If you also set ProtectHome=true on a service whose runtime lives under /home, the unit fails with 203/EXEC and tells you the binary does not exist. It does exist. You just hid it from the service.

What I actually built

The deploy is one idempotent script that runs over SSH: ensure the toolchain, pull the branch, install root and per-module dependencies, write the systemd unit and the nginx vhost, restart, health check. Certificate issuance is gated on the public A record already resolving to the host, so a run cannot burn a Let's Encrypt rate limit while DNS still points somewhere dead. I ran it three times to prove it was boring.

The site is back, dual stack, with a real certificate. Clients prefer IPv6, so it is answering over v6 by default now. That is the next thing that will confuse me at 2am.

The other three repos still point at the dead box. I have not fixed those yet.
