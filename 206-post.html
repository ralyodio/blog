Tuning a production box with 334 containers and no memory limits

2026-10-01, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes, then edited by me.

back to my blog postings

One of our production servers runs most of the fleet: 32 cores, 91 GB of RAM, 334 Docker containers, one shared Supabase Postgres that a dozen apps talk to, and not a single mem_limit in the compose files. This morning it was down to about 3 GB available, swap was 100% full, and the apps kept logging "the database system is in recovery mode".

By the afternoon it had 32 GB available. Nothing got bigger. Here is what we changed and the tools we used to find it.

Watching it: hqtui-demo

I gauge a box with hqtui-demo, the demo app for hqtui, our terminal UI library. On Linux it reads /proc, the systemd units, sshd logins from the journal and the nginx access log, so it is a live view of the real machine and not a canned animation.

npm i -g @profullstack/hqtui-demo hqtui-demo

I keep the dashboard sorted by memory (F6), the services screen open for crash loops, and the traffic screen for whatever is hitting nginx. I don't trust a fix until the numbers move on that screen.

1. earlyoom was killing Postgres

The box runs earlyoom with an --avoid regex so it never touches the database. The regex said postgres. The Supabase image runs Postgres as .postgres-wrapp, because the kernel truncates process names to 15 characters. So it was never avoided.

journalctl -u earlyoom showed 16 SIGKILLs of Postgres in a day, each one a full crash recovery, plus 1,334 SIGTERMs to the checkpointer. Adding \.postgres-wrapp to the avoid list stopped it.

Two traps if you set this up yourself. systemd reads EARLYOOM_ARGS from the env file with no shell quote removal, so --avoid '^(sshd|postgres)$' passes the quote characters into the regex. Write it unquoted. And the service starts fine either way, so check the real arguments with ps -o args= -C earlyoom.

2. shared_buffers was 23 GB

Postgres was the biggest thing on the box at 25.5 GB. That was not a leak. shared_buffers was set to 23336MB. The per-backend RSS of 4 to 5 GB that made earlyoom think each connection was a monster is the same shared pages counted again in every process.

We capped it at 8 GB and set per-tenant connection limits (one app was holding 126 of the 300 connections). The tuning lives in a script, so the next box gets it too. Check the value after the run, not the exit code. Our first run copied an old version of the script and happily wrote 23336MB back.

3. A worker spinning on a missing dependency

One worker sat at 3.4 to 3.8 GB within 25 seconds of starting and had restarted 4,292 times. BullMQ 6 made ioredis an optional peer dependency. The repo never installed it, so the worker failed to load it and retried about 6,000 times a second, forever, ignoring SIGTERM.

Adding ioredis and a circuit breaker on the error path took it to 70 MB and zero restarts. If you are on BullMQ 6 or later, list ioredis yourself.

4. Sixteen Node workers sized from the host

Our RSS Amplifier web service forks one Node worker per CPU, reading the count from the cgroup. On this box the containers have no cgroup limits, so it read the host: 32 CPUs, 91 GB. It started 16 workers with a 3.5 GB heap each. Lazy GC under a high ceiling let each one drift to about 970 MB over six days, 11.7 GB in total.

Now it runs at most 4 workers and splits one 4 GB heap budget between them. After the deploy: 5 processes, 605 MB.

The load that is not yours

A decent production load includes people you did not invite. ThreatCrush runs as a root daemon on every box and bans from nft.

The nginx log had 189,000 paywall 402s from 111,576 IPs, about 1.7 requests each. No per-IP rule catches that, and the single busiest address was real Googlebot, which you must not ban. So ThreatCrush rules can now group by endpoint instead of IP and alert on the crowd, and the real cap is an nginx limit_req zone with a constant key that limits total throughput on the expensive route.

For the attackers it can name, bans now double from 5 minutes up to 7 days and strikes are remembered for 30 days.

One more lesson from today. Our own CLI login polled the server every 3 seconds and got a 400 back while waiting, as the OAuth device flow spec says. That is 20 errors a minute, which is exactly what the scanner rule looks for, and the box banned four of our own servers. Pending is a 202 now, and every fleet IP is on the protected list. If your own daemons poll an endpoint, a routine state must not be a 4xx.

What I would do first on any box

  • Sort by memory and ask why the top five are that big. Usually it is configured, not leaked.
  • Read journalctl -u earlyoom (or journalctl -k | grep -i oom) before blaming the app.
  • Size workers and heaps from a budget, never from os.cpus() on a box without limits.
  • Count requests per IP before writing a per-IP rule.
