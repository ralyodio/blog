The line is only there before the game

2026-09-07, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes, then edited by me.

back to my blog postings

tipoffwatch.com now shows the betting line on a game before it starts, and a proper recap after it finishes. Box score, score by quarter or inning or set, the leaders, and the wire recap where an agency covers the league. There is a Final scores page, and every league and team page has a recent results section.

None of it costs a single extra request to the provider. Every fact was already inside responses the sync was fetching and throwing away. There is a comment in our code, written months ago, describing the summary endpoint as carrying "a boxscore, rosters, odds and news we do not use." That comment is now wrong, which is the nicest way for a comment to become wrong.

The interesting part is the odds.

ESPN publishes a line on the scoreboard, on the same response we already pull for every league, so reading it is free. It is only there while the game has not started. I measured it this morning against the live API: 16 of 16 NFL games had a line, 5 of 5 WNBA, 4 of 4 college football, all of them before kickoff. Every finished game in the four leagues I sampled had none. Twenty one finished college football games, fifteen finished baseball games, zero odds between them.

A book stops pricing a game when it starts, and the provider drops the field with it.

So there is no reading the line later for the page that most wants it, which is the recap. It has to be written down before kickoff and kept. Both places that write a fixture now coalesce rather than assign, because the first sync after kickoff carries a null where the line used to be, and an assignment would erase it at exactly the moment it became worth having. The minute by minute score tick is the important one there. It sees a fixture every sixty seconds right up to the whistle.

Soccer has a nice trap in this. A finished match does not return an empty list of odds, it returns a list with one entry, and the entry is null. It looks like data. Any check written against the length of the array passes.

Two more things I would have got wrong without measuring them.

Team statistics come in two different containers. Football, soccer and Australian football ship a flat list of label and value. Baseball and rugby league ship it grouped, with the actual numbers one level further down. If you read only the flat one, which is the obvious one, baseball gets an empty comparison table and nothing tells you. We had already been bitten by exactly this shape with play by play, where the plays live under three different keys depending on the sport, and I still nearly did it again.

The other one is worse, because the wrong answer looks principled. We have a flag on each league saying whether it supports play by play, set after measuring which sports return a log. Ten sports do not. It is tempting to reuse that flag to decide who gets a box score, since it is already there and already means "this sport is thin." It is exactly backwards. Six of those ten return a box score and nothing else. Volleyball, water polo, field hockey, rugby, rugby league, lacrosse. Gating recaps on the play by play flag would have denied a box score to precisely the sports where the box score is the only thing there is. They needed their own flag, and now a volleyball match gets a recap page it could never have had a play log for.

Then I shipped a bug and found it by looking at the live page.

The results list is ordered newest first, bounded to the last week. I put a lower bound on the kickoff time and no upper bound, because a game that has finished is obviously in the past. The provider does not agree. It marks some future dated fixtures as finished, usually a postponement it has closed out. With only a lower bound those sort to the very top of a newest first list and stay there forever, because nothing else ever outranks them. Five of them were sitting above every real result, dated up to eleven days out, on a page I had just announced as working.

The fix is one line. A game cannot have finished before it started.

The regression test for it is the part worth mentioning. I wrote an assertion that the query contains the new bound, ran it, and it passed. Then I deleted the fix and ran it again, and it still passed. Another query in the same file already contained the string "starts_at <= now()" as part of a longer expression, so the file wide check matched whether or not my query had the bound at all. A test that cannot fail is not a test. Scoping it to the one function made it real, and deleting the fix then failed it properly.

I have started deleting the fix as a habit. If the test still passes, the test is decoration.
