I’m a 1000x engineer now

2026-11-25, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes, GitHub stats and session logs, then edited by me. Yes, that is part of the point.

David Veszelovszki wrote a great essay called I’m a 100x engineer now. It took second place in The Pragmatic Engineer’s essay challenge, and it deserved to. He builds one file manager, mostly alone, at around 10,000 lines a day. He paints his kids’ room while Claude closes 42 issues. Go read it.

Then come back, because I think 100x undersells it. Here is my version.

The old math

For most of my career, here is what it took to ship a real product, the kind with users, payments, an API and something running on servers:

  • About $2M of seed money.
  • About six engineers, plus a designer and someone pretending to be a PM.
  • About two years to get from a deck to something people pay for.

Six engineers for two years is roughly 3,000 engineer-days, once you take out weekends, holidays, standups, offsites and the week everyone lost to a Kubernetes upgrade.

If one person ships the same thing in one day, that is not 100x. That is 3,000x. I call it 1000x because I round down and because nobody believes the real number anyway.

Saturday

Here is an actual day, 2026-11-22.

Before breakfast I asked for live streaming on c0mpute, our peer-to-peer compute network. Not a demo. By evening it was running in production:

  • A hosted RTMP ingest server, so you point OBS at it and go live.
  • Every node on the network can now relay video, and each relay signs a receipt every 60 seconds.
  • Those receipts settle as real money: $0.01 per GB, 95% to the person whose machine did the relaying, with spending caps so nobody gets a surprise bill.
  • A free tier, docs, an API, an MCP server tool, an OAuth scope.
  • Integrations into three of our other products the same day: PairUX can broadcast to it, nixamp plays streams as TV channels, and our AI board-meeting app publishes meetings as live calls.
  • Tested end to end: a bad stream key gets refused, a real RTMP push comes out as HLS on the gateway, receipts get filed.

That is a decentralized Twitch with a payments layer. People raise rounds for less. Companies have spent years and tens of millions on exactly this.

The same afternoon an agent also researched a consumer banking app, worked out what infrastructure sat underneath it, filled in a partner’s sales form and shipped a non-custodial US bank account module for CoinPay, dark, with tests. I wrote that one up already. That was a side quest.

The numbers

Lines of code is a bad metric and David is honest about using it anyway. I’ll use GitHub’s own counters, which are also bad, but they aren’t mine:

  • 100,815 contributions on my account in the last twelve months. That is about 276 a day, every day, weekends included.
  • Of those, 21,799 were public commits, 8,842 were pull requests, and 69,727 were in private repos.
  • 7,470 in the last 30 days alone.
  • The Profullstack org has 371 repositories. 329 of them got a push in the last month.
  • Our house stack is dozens of products: payments, security, hosting, podcasts, search, an ad network, a BBS. Each one has a web app, an API, a CLI, a TUI and an MCP server, because that is the rule.

The company is me. Plus agents.

How it actually runs

David uses one terminal, no skills, few rules, and never reviews code. I went the other way on almost everything, and I think that is why the multiplier is different. He is one very fast engineer on one product. I’m running a portfolio.

  • Many sessions at once, in the background. Each one gets its own git worktree, works the task to the end, opens the PR, merges, releases, deploys and checks the live site. Then it reports back. I check in between other things.
  • Standing rules instead of prompts. I don’t write specs. I write rules once and every agent reads them: never run services as root, never put pit.world wording on a normal domain, never buy anything without an explicit yes, never hold customer money. A good rule is worth a thousand prompts.
  • Memory. Every gotcha gets written down where the next session will find it. When a deploy breaks because someone moved a git tag, that becomes a note, and it never breaks that way again. David calls this “structurally eliminating a class of bug”. Same idea, applied to operations instead of code.
  • The agent has a name. It’s riotcoder. It has its own email, its own accounts, its own git identity and its own profile. It co-hosts the podcast. When it signs up for something, it signs up as itself.
  • Agents drive everything with an API, and a browser for the rest. DNS, servers, payment providers, npm, app stores. If there’s no API, it drives a desktop. I mostly show up for CAPTCHAs.

One thing David and I agree on completely: guardrails are the job. He spends 40–50% of his time on checks and architecture. I spend a similar share on rules, memory and fleet hygiene. The agents are only as good as the walls you build around them.

Why the multiplier keeps going up

A team of six doesn’t ship 6x. It ships maybe 3x, because half the time goes to talking to each other. Every engineer you add brings more meetings, more handoffs, more “who owns this”.

Agents don’t have that problem. Ten parallel sessions don’t need a standup. They share a memory, a rulebook and a git history. The coordination cost that used to eat half of every startup is close to zero.

And because everything is built on the same house packages, each new product starts out already wired to payments, auth, analytics, email and the rest of the fleet. The 50th product is cheaper than the 5th. That is where 100x turns into 1000x: not typing faster, but compounding.

The bill

It’s not free, and I’d be lying if I said it was all upside.

  • Security is now the whole game. This month we had real intrusions: a leaked key in a dotfiles repo, an injection through a GitHub Actions workflow, a stolen app key. More surface, more keys, more agents with access means more ways in. I wrote post-mortems on each one. Give agents broad access and you had better have backups, rotation and someone watching.
  • Breadth costs maintenance. 371 repos means something is always broken somewhere. Disks fill up. Certificates expire. A Redis instance leaks 66 GB of temp files. The agents fix most of it, but someone has to notice.
  • Revenue doesn’t scale like code does. I can ship a product in a day. I can’t make a market want it in a day. Distribution is now the bottleneck, by a mile.
  • Sleep. David is right that this feels like a slot machine. There is always one more thing you could kick off before bed. Take care of yourself.

So what am I?

Not a coder, really. I said it in my last post: I’m a button pusher. But I push a lot of buttons, for a lot of products, and every one is backed by twenty-some years of getting burned.

What used to need $2M, six engineers and two years now needs a person with judgment, a good rulebook and a day. That is not a prediction. That was last Saturday.

If you’re working this way too, I’d like to compare notes. What is your real multiplier, and what broke when you scaled it up?
