cli-tools picked up two commands this week. mail reads and sends over IMAP and SMTP. cal reads and writes calendars over CalDAV. Neither needed much protocol work. The part that took the thinking was the password.

Nobody tells you which password

Gmail refuses your account password over IMAP. On purpose. So do Yahoo, AOL, iCloud, Fastmail and Yandex. Each one wants a generated app password, each one keeps that page somewhere different, and when you type the wrong password the server says something that reads like a typo. You try again with the same password, slower.

So mail login prints the rule before it asks:

$ mail login gmail you@gmail.com
Gmail / Google Workspace takes an app password, not the account password.
  an App Password from https://myaccount.google.com/apppasswords (needs
  2-step verification on the account); the normal account password is refused
  https://myaccount.google.com/apppasswords
password:

Then it tries IMAP and SMTP before it stores anything. A refused login stores nothing, because a stored password that does not work moves the failure somewhere further from the cause. If reading works and sending does not, it stores the account and says so.

Fifteen providers are built in for mail, nine for calendar, plus a custom option that takes hosts or a URL. The address usually names the provider on its own. A custom domain does too: mail login you@yourdomain.com reads the domain's MX records, and a domain parked at Google, Zoho, Fastmail, Proton, iCloud or Forward Email identifies itself.

Four hosts you cannot reach at all

This was the other half of the work, and it is the half that saves the hour.

Outlook.com, Hotmail and Microsoft 365 take only OAuth2. Microsoft removed basic authentication for Microsoft 365 IMAP in 2022 and for personal accounts in September 2024, and app passwords stopped counting at the same time. Tuta and HEY never had IMAP. Proton has IMAP only through its paid Bridge, and no CalDAV on any plan.

Google Calendar is the one that gets people. A Google app password opens Gmail over IMAP just fine. The CalDAV endpoint next to it takes only OAuth2, so the same password that reads your mail cannot read your calendar.

None of those attempt a login. They print the reason:

$ cal login google me@gmail.com
cal: Google Calendar cannot be reached with a password: Google's CalDAV
endpoint takes only OAuth2 tokens; an app password opens Gmail over IMAP
but not the calendar. Use a client with Google sign-in.

cal has no dependencies

CalDAV is three requests. PROPFIND finds the principal and the calendars. REPORT reads a window. PUT and DELETE write. The XML that comes back is shallow enough to read without a parser, and the server expands recurring events if you ask it to, so a weekly standup lists on every day it happens and there is no RRULE code in the repo.

$ cal ls --week
Mon 2026-09-07
  10:00-10:30  Standup  [Work]
  12:00-13:00  Lunch  @ Cafe
Tue 2026-09-08
  all day      Offsite  @ Lake house

Times go in the way people type them. --at "tomorrow 9:30", --at "friday 2pm", --at 2026-09-10 --all-day --for 2d. A weekday name means the next one, never today.

Most providers use one password for mail and calendar, so cal login forwardemail --like work borrows it from the mail account and skips the prompt entirely.

The certificate

Proton Bridge listens on localhost with a certificate it signed itself, and the shortest way past that is to turn certificate verification off. The first version did exactly that, and the credential scanner flagged it within a minute of the pull request opening, which was the correct call. Verification stays on now. The account pins Bridge's own certificate instead, found at the path Bridge writes it to, and a pinned path that cannot be read is an error at connect time rather than a quiet downgrade.

Both commands are in cli-tools, v0.26.0.
