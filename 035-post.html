This works right now, from a normal shell, with a stock curl and no flags:

$ curl -s https://alt.2600 | pandoc -f html -t gfm
alt.2600

# alt.2600

served over Moshpit.

alt.2600 is not a domain. Ask a public resolver for it and you get nothing back, because .2600 is not in the ICANN root and never will be. It still answered, over HTTPS, with a certificate my machine accepted.

That is the Moshpit, and it is far enough along to hand out. You can register a name at app.moshcode.sh/pit today.

What you are actually buying

The namespace is one level deep and first come first served. You claim an ending, and every name under it is yours to mint for nothing. Hold .eggs and blue.eggs, scrambled.eggs and anything else you think of are yours, forever, at no extra cost.

Five dollars an ending, two dollars a name, paid once. Nothing renews and nothing lapses. No name you hold can drop because an invoice went to an address you stopped reading, which is the single worst property of the system this one sits next to.

As of this morning there are 17,968 endings claimed and 17,760 of them are for sale. You can also point an ending at another one you own, so .agentic aliased to .agent makes foo.agentic resolve to foo.agent, with any name you exempt staying where it is.

Turning it on

One command, on any machine that should see these names:

sudo moshcode dns enable

That routes Moshpit endings to a local bridge, installs the local CA so HTTPS verifies, and points names at the pinned proxy. There are --no-trust and --no-proxy if you want less of it. moshcode dns status reports the bridge and the routing separately, which is the triage command when something looks wrong.

It is deliberately not automatic. The installer does not do it, upgrading does not do it, and no other command does it as a side effect. Rewriting somebody's resolver without being asked is how you break their machine, and we did break one that way once.

The other half of that policy is that clearnet wins by default. The resolver only answers where the legacy root has nothing, so a name that already works keeps working and the pit never gets to shadow it. A resolver that silently redirected a domain you could already reach would be indistinguishable from a hijack. If you want the pit to outrank DNS you have to ask for it by hand.

Hosting something at a name

Put your server's IPv6 address in the "points at" box, or a hostname. IPv4 literals are refused on purpose: an A record on a small host is usually leased or NATed and goes stale without telling anybody. Then serve the name on port 80:

server {
  listen [::]:80;
  server_name seo.rank;
  root /var/www/seo.rank;
}

Caddy wants http://seo.rank { ... } and the scheme is required rather than a typo. No public CA will issue a certificate for an ending that is not in the DNS root, so Caddy's automatic HTTPS has to stay off. That is also why the trust step above exists, and why it is honest to describe this as a local CA rather than as HTTPS in the sense you are used to.

The browser connects straight to your box and sends Host: name.ending. Nothing proxies and nothing redirects. A port other than 80 only works in the pit's own /n/ view, because DNS carries an address and has nowhere to put a port.

If you do not run a server, paste an RSS or Atom URL into the feed box on a name you hold and the pit draws the site for you. Blog feeds render as posts, podcast feeds render as episodes with a player, and it is cached for a few minutes so a name that gets linked somewhere busy does not become traffic on your feed host. A name with both a target and a feed serves the target, so the feed doubles as a soft landing for a site that has gone down.

There is a publish API too. One POST, bearer token, upserts on the slug, so a webhook that fires twice updates one post instead of making two.

What beta means here

Pointed names work. alt.2600, chovy.hacker and seo.rank all return 200 with a clean TLS verification on a machine that has run dns enable.

Parked names do not have HTTPS. curl https://blue.eggs fails the certificate check, because nothing has issued one for a name that does not point anywhere yet. Over plain HTTP it does the right thing and 302s to its page on the pit, which is a fix from last week, and before that it landed on a Railway 404 instead.

So: names resolve, names serve, names have certificates once they point somewhere, and the parking path stopped lying. That is enough to be worth claiming an ending over.

app.moshcode.sh/pit. Bring moshcode 0.63.0 or newer, and read what dns enable prints before you agree to it.
