Bun vs Node.js in late 2026: the benchmarks disagree, so measure your own

2026-10-06, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes, then edited by me.

back to my blog postings

We ran "bun vs node" through our own search tool, which asks Ceramic, Exa and Linkup at once and ranks what they agree on. The five pages it put on top are all confident. They are also wildly inconsistent: depending on which one you read, Bun is four times faster than Node.js or fourteen times slower.

Both claims are true. They just measured different things.

What each source measured

| Source | Test | Bun | Node.js | | --- | --- | --- | --- | | Alex Aslam, DEV (Jun 2025) | HTTP server, Bun 1.0 vs Node 20 on EC2 | 28,000 req/s | 8,000 req/s | | Better Stack (Jan 2026) | Express throughput | 52,479 req/s | 13,255 req/s | | Bun's own benchmark, via Strapi | Bun 1.4 vs Node 26.7, bombardier | 48,243 req/s | 25,181 req/s | | JCSI peer-reviewed study, via Strapi | I/O-bound workload | 27,500 req/s | 28,200 req/s | | Platformatic (Jan 2026), via AlexHost | Next.js on AWS EKS, average latency | 233.76 ms | 16.44 ms |

Generalist Programmer, also in the top five, says 3 to 4x faster without naming a test. The first three rows are hello-world servers. They measure the HTTP layer and very little else, and Bun's HTTP layer is genuinely fast. The last two run something closer to a real application, and the gap closes or flips.

Why the numbers move

Allocation-heavy code is where Bun loses ground. A Bun GitHub investigation cited by Strapi measured 36,887 vs 26,050 req/s in Bun's favor on hello-world, then 11,800 vs 16,200 in Node's favor once the handler churned objects. A later Bun PR cut that penalty from 33% to 8%, but it shows the shape of the problem.

Memory flips too. The DEV post measured 95 MB for Bun against 210 MB for Node on a small service. Strapi found a Next.js standalone server on Bun 1.4.0 at 179 MB after startup and 318 MB after 45 idle seconds, against 80 MB on Node 24.

Where Bun is clearly ahead

Installs. Bun's benchmark on a project of about 220 packages: 1.41 s for a cold install, against 13.49 s for pnpm and 18.12 s for npm. The DEV author saw 0.4 s against 12 s. Nobody disputes this one, and it is the easiest win to take.

TypeScript. Bun runs .ts files with enums, namespaces and decorators, no config. Node 24+ runs TypeScript natively too, but only erasable syntax: annotations and interfaces, not enums.

One binary. Bundler, test runner, SQLite, a Postgres client and an S3 client ship inside Bun. On Node that is four or five packages and their configs.

Where Node is still ahead

Compatibility. Bun 1.4 passes 97% of Node's tests for node:http, node:fs and node:stream, and 94% for node:http2. The DEV author hit bcrypt failures; Strapi lists bcrypt as unreliable and sharp with open segfault reports. As AlexHost puts it, the last 5% can be the whole project.

Observability. Datadog, New Relic and OpenTelemetry do not officially support Bun. If your on-call depends on an APM, that decides it.

Security. Node has an opt-in --permission flag, with bypasses its own docs admit to. Bun has no runtime sandbox at all; its "Secure Mode" PR was closed in June 2026.

Hosting. AWS Lambda has managed Node 22, 24 and 26 runtimes and no managed Bun runtime.

One from our own repos

We run Bun on the repos that pin it. The gotcha that cost us the most time was not speed: Bun's built-in Postgres client sends a JavaScript array as the string a,b instead of a Postgres array, and the query then fails with one of three unrelated-looking errors. Every runtime has a list like this. Bun's is shorter than it was, but it is still being written.

How to choose

  • New service, CLI or internal tool: Bun. The install, startup and TypeScript wins are real, and you have no legacy native modules to trip over.
  • Next.js, an APM-dependent service, Lambda, or anything using native addons: Node.
  • An existing Node app: keep Node as the runtime and use bun install and bun test for speed in development and CI. Strapi recommends exactly this split for its own stack.

Whichever way you lean, run your real handler under load before you switch. Every number above is someone else's workload.
