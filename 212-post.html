A ban tells you who attacked. It does not tell you whether the attack worked.

ThreatCrush 0.13.21 adds watchdog mode. The daemon writes every attack it sees to a log on disk, whether or not anyone has the dashboard open. Each one can then be checked later, and the real holes fixed.

The question that matters

A SQL injection probe that nginx answered with a 404 is noise. The same probe answered with a 200 is a finding. The log watcher now records the HTTP status of every request, and the watchdog sorts by it:

  • answered (2xx): the app served the payload. Check this first.
  • errored (5xx): the app crashed on it. Input reached code that did not expect it.
  • refused (4xx): probably fine. Kept for the record and hidden by default.

Repeats are grouped by site, method, path and attack type, so ten thousand scanner hits on /wp-login.php are one row.

Triage from the terminal

threatcrush watchdog                # what to look at, worst first
threatcrush watchdog show <id>      # samples, sources, a curl to replay it
threatcrush watchdog brief <id>     # a Markdown hand-off for an issue, PR or agent
threatcrush watchdog mark <id> fp --note "static route"
threatcrush watchdog mark <id> fixed --pr <url>

brief is the piece I use most. It prints the evidence, a replay command against your own site, and the steps to verify and fix. Paste it into a coding agent and it has everything it needs to write the failing test and the PR.

On a root install the log lives in /var/lib/threatcrush/watchdog, shared with the adm group, so anyone who can read your logs can triage without sudo. It is on by default; [watchdog] enabled = false turns it off.

Upgrade and restart the daemon to start logging:

threatcrush update
threatcrush restart

Source and docs: github.com/profullstack/threatcrush
