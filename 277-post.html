Post-mortem: how an attacker got a shell through our Postgres

2026-11-20, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes and the incident log, then edited by me.

back to my blog postings

On November 19 someone got into one of our shared build servers. It started as a boring alert: eleven containers went unhealthy at once and our autoheal watchdog refused to restart any of them, because that many failing together points at the host, not the apps. It was right. The shared Postgres had crashed and restarted itself twice in eight hours, and when I went looking for why, I found shell commands in the database container's log that we never ran.

What happened

  • A private SSH key was committed to our dotfiles repo on November 14. The repo is private, but "private" means everyone with org read access, and that list had grown.
  • Our self-hosted Supabase stacks published Postgres on every interface. Docker writes its own iptables rules, so a published port skips ufw entirely.
  • We had already locked those ports down in October. The rules were never saved, so the box came back from a reboot on November 18 with the database open to the internet.
  • The attacker had the superuser password, a 48 character random string. It was not guessed. They logged in, used COPY ... FROM PROGRAM to run commands as the postgres user, port-scanned from inside the container, and used the stolen key to reach the host.

The two crashes were their payloads dying. Postgres treats an abnormal backend exit as a reason to reset every connection, so each attempt knocked every app on that database offline for a minute or two.

What our tools missed

The database logged 10,150 failed logins in three days from about 60 addresses. Our intrusion daemon banned none of them. It reads the systemd journal, and Docker containers log to their own JSON files, so it never saw a single line. Those failures turned out to be internet background noise, not the attacker. The attacker logged in on the first try, and a throttler would not have stopped that. It still should have seen the noise.

We also run Postgres with log_min_messages=fatal to keep logs quiet, which hid the one line that names the signal that killed a backend.

What we changed

  • The DB ports are dropped in the DOCKER-USER chain, which is the chain Docker actually respects. A small unit rebuilds that chain every time Docker starts, so a reboot cannot quietly undo it.
  • The superuser can no longer log in from 0.0.0.0/0. Only local Docker networks and our own servers.
  • Rotated the shared database password across 42 vaults and 71 containers, the database's JWT signing keys, the vault identity key (505 vaults re-keyed), the host SSH key on every server and on GitHub, console passwords per box instead of one fleet default, and 87 app secrets our vault rotates on its own.
  • Rebuilt the database container from its image so nothing they dropped in it survives.
  • The leaked key is out of every authorized_keys and is being purged from the repo history.
  • Our intrusion daemon, ThreatCrush, now reads Docker container logs through the Docker API and bans an address after 5 failed Postgres logins in 10 minutes. It also preloads the Tor exit list for SSH instead of waiting for a bad login, because a stolen key never produces one.

What I would tell you to check today

Run docker ps --format '{{.Ports}}' | grep 0.0.0.0 and look for any database port. Then check that your firewall rules for those ports exist right now, not just in a file. And grep your dotfiles repo for PRIVATE KEY, including history.

If you run self-hosted Postgres behind Docker, how do you keep it off the internet across reboots? I would like to know what holds up for you.
