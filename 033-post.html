Why I built DiskPush

FileZilla is a good file browser. It is also perfectly willing to re-upload three hundred megabytes because I changed one file in the folder. rsync has not done that since the nineties, but reaching for rsync means remembering which of its couple hundred flags I wanted, and getting the trailing slash right, and quoting a remote path that has a space in it.

So I went looking for the obvious product: a two pane file browser that transfers with rsync. The rsync GUIs I found are shaped like backup job editors. They are built around saving a profile and scheduling a nightly run, not around opening a server, looking at it, and pushing a directory right now. The file managers I actually liked were the other way round: good panes, SFTP underneath, file by file, no idea what changed.

Nobody had built the middle. So we built our own, with blackjack.

The product is the defaults

The point of DiskPush is that you should not have to know rsync to get rsync behaviour. This:

diskpush ./dist/ prod:/srv/app/

runs exactly this:

rsync --archive --partial-dir=.rsync-partial --human-readable \
      --itemize-changes --info=progress2 ./dist/ prod:/srv/app/

Metadata preserved, interrupted transfers resume from their partial data, unchanged files skipped. Re-running a finished job moves almost nothing, which is the entire reason to want rsync in the first place. And diskpush --print-args prints the command for any job before it runs, so you never have to take my word for what it is doing.

Server to server, with nothing in the middle

A single rsync process cannot have two remote endpoints. That is why most tools quietly pull the files down to your laptop and push them back up. DiskPush connects to the source host and starts rsync there, with the destination as its remote:

diskpush server-a:/data/ server-b:/backup/

The payload goes A to B over rsync's own SSH connection. My desktop holds the control session and reads progress off it. Directory listings and progress counters cross my machine because the panes have to render. File contents do not, and there is no DiskPush relay for them to cross instead.

Built to be handed a delete flag

The other reason I wanted to own this: a mirror mode is a foot gun and I wanted to hold the trigger.

rsync is spawned with shell: false and an argument array, so a path containing backticks or a semicolon is a path. Remote arguments get --protect-args against anything older than rsync 3.2.4, because without it the remote login shell expands the remote path and your directory named $HOME backup becomes two arguments. A delete-enabled job cannot be constructed until its dry run has been reviewed. And -- --delete in the pass-through is refused outright, because it would turn a sync into a mirror behind the preview that exists to stop exactly that.

Two things I got wrong

The packaged desktop app shipped with an empty node_modules for a while. electron-builder was doing its own install inside the staging directory and pnpm's symlinked layout did not survive the copy, so the bundle looked right and started to nothing. And the launcher crashed on boxes where the Chromium sandbox cannot start, which is most sandboxed build environments and was every machine I tested the installer on.

Both are fixed in 0.1.2, which is where it is now.

curl -fsSL https://diskpush.com/install.sh | sh

Installs the CLI, and the desktop app if the machine has a desktop. Everything lands under your home directory, no root and no package manager. Add -s -- --cli-only on a server. It needs rsync and an SSH client locally, and rsync on whatever it talks to.

MIT, source at github.com/profullstack/diskpush, docs at diskpush.com.
