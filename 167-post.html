The pit signs now: one root for every Moshpit name

2026-09-18, by Anthony “chovy” Ettinger.

No public certificate authority will ever issue for a name outside the ICANN root. That is not a policy anyone can appeal; it is what the root programs are for. So https on a Moshpit name has meant a self-signed certificate per origin, a fingerprint of its key published by the registry, and every client learning every name one at a time. It worked. It also meant that a browser had to be taught each site before it would open it, and the teaching kept finding new ways to fail.

Today the registry became a certificate authority.

Why the registry

A CA has one real job: knowing who a name belongs to before it signs. The pit already does that job. It is where names are claimed, sold, leased and pointed, and it is the only party that can say with authority that blue.eggs is yours and red.eggs is not. Everything else a CA does is key handling. So the registry signs, and the question of trust moves from "have I learned this name yet" to "do I trust the pit". Answer that once and every name follows.

What gets signed, and for whom

An origin asks for a certificate by sending a signing request for its name. The registry checks that the account asking is the one that controls that exact name: the holder, or the tenant while a lease runs. That rule is what makes resale safe. Whoever owns the .foo ending cannot get a certificate for bar.foo once it has been sold, and ending owners never hold a signing key at all. Only the registry signs.

The certificate names the host and everything under it, is valid for thirty days, and cannot itself sign anything. Short lives are what make revocation unnecessary: a compromised key is out of the world within a month and is simply not renewed. The subject comes from the name, never from the request, so a request for blue.eggs cannot come out naming red.eggs however it is written. Names whose ending is a real top-level domain are refused unconditionally, whatever the registry's own tables say, so a bug cannot mint google.com. And every certificate's key is still published as a pin, so anything that checks pins keeps working.

Where the root goes

The root's private key signs the issuing certificate once and then stays cold, in the vault. The registry holds only the issuing key. The root certificate itself is public: curl https://pit.moshcode.sh/api/moshpit/ca.crt.

moshcode dns enable now installs it, into the browser store without root and into the system store with sudo, and moshcode dns ca does only that for a machine whose resolution comes from somewhere else. TronBrowser fetches it on install and on every upgrade and trusts it on every start. On an origin, setup-origin.sh asks the registry to sign, serves the chain, and installs a daily timer that renews before day thirty. Nobody has to remember a step.

What it does not do

Stock Chrome on a stranger's laptop will not trust .hacker, because public root programs only admit CAs for names under the ICANN root. That limit belongs to the namespace, not to this CA, and it is the same limit every private CA lives with. The root also carries no name constraints, since X.509 cannot say "everything except the ICANN root" across seventeen thousand endings and counting. What bounds it is the signer, which is why installing the root is an explicit act in every client and never something a resolver does on its own.

The registry side is in moshcoder/moshcode, documented at apps/pwa/docs/moshpit-ca.md. The client half shipped as moshcode 0.102.0, the browser half as TronBrowser 3.14.0, and the origin script in moshpit-proxy.
