One truncated JSON response, one page broken forever

2026-09-07, by Anthony “chovy” Ettinger.

How this was written: drafted with an AI assistant from my own notes, then edited by me.

back to my blog postings

brisk.news summarises any article you paste at it. One article, and only one, crashed the page. Not an error message, a white screen.

The summariser is gpt-4o-mini with response_format: json_object, and a prompt asking for a title, a summary of two or three paragraphs, and five key points. The result was parsed and cast straight to the TypeScript type:

const summary: ArticleSummary = JSON.parse(responseText);

That cast is a lie. JSON.parse returns any, and the type declares keyPoints: string[], so from that line onward the compiler believes in a field the model never promised.

max_tokens was 1500. Two or three paragraphs plus five key points does not reliably fit in 1500 tokens. The model got as far as the title and most of the summary, ran out of budget, and stopped. What came back had two keys, title and summary, and the summary text ended in the middle of a sentence.

Then the part that made it permanent. That object was written to the cache. Redis for eight hours, Supabase forever.

The renderer does this:

{summary.keyPoints.length > 0 && (

undefined.length throws, and it throws during render, so React unmounts the tree instead of showing anything. That is why it presents as a crash rather than as an error. Because the bad object was cached permanently, it threw on every load of that URL from then on.

One row out of 112 was in this state. That is why exactly one article was broken while every other one worked, and why it reproduced every single time.

The fixes, in order of how much they matter.

Check finish_reason. If it comes back as length the response is truncated and must not be cached. A permanent cache with no validation on the way in means one bad generation is one permanently broken URL.

Raise the token budget. 1500 was never enough for what the prompt was asking for.

Normalise on the read path as well as the write path. This is the one worth stealing. Poisoned entries were already sitting in Redis and Supabase, and the Redis host is internal to the platform, so I could not reach in and delete the key from outside. Normalising inside the cache read meant the already-cached garbage rendered safely the moment the deploy went out, with no purge and no waiting out a TTL.

Two things I would rather have known an hour earlier. A type assertion on parsed JSON is not validation, it is just a note to the compiler. And a cache is a machine for converting a transient failure into a permanent one.
